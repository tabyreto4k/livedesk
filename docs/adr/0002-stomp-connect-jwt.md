# 0002. JWT приезжает заголовком STOMP CONNECT

Статус: принято · Заход 2 · [Р4]

## Контекст

WebSocket-рукопожатие в браузере заголовки не принимает: `new WebSocket(url)` не даёт
поставить `Authorization`, SockJS-фоллбэк — тем более. Токен всё равно нужно проверить до
того, как сессия начнёт получать чужие сообщения.

## Решение

Рукопожатие пускается без токена, а авторизуется первый STOMP-фрейм: `CONNECT` несёт
заголовок `Authorization: Bearer <jwt>`, `StompAuthInterceptor` проверяет подпись и срок,
кладёт `AuthenticatedUser` в сессию как `Principal` и отклоняет фрейм, если токена нет или
он непригоден. Дальше все фреймы сессии идут от найденного пользователя — повторно токен
не разбирается.

## Последствия

Токен не попадает ни в access-лог nginx, ни в лог сервера, ни в историю браузера. В
`SecurityConfig` путь `/ws/**` открыт — это осознанно: рукопожатие ничего не отдаёт, а
единственный способ что-то получить — пройти CONNECT.

Отказ выглядит как обрыв соединения на CONNECT, а не как HTTP 401: клиент видит ошибку
STOMP-кадра. Для фронта этого достаточно, для внешнего API было бы мало.

## Альтернативы

**Query-параметр `?token=`.** Работает везде, включая SockJS, и ровно поэтому токен
оказывается в access-логах и в реферерах — известная дыра.

**Кука.** Завязывает WebSocket на домен и тянет за собой заботы про CSRF, ничего не давая
взамен: сервис stateless, сессий нет.
