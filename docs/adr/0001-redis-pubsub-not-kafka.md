# 0001. Межинстансная доставка — Redis pub/sub, не Kafka

Статус: принято · Заход 3 · [Р3]

## Контекст

Клиент и оператор сидят на разных инстансах chat-service: WebSocket-сессия живёт в памяти
того процесса, который её принял. Сообщение, принятое инстансом A, обязано дойти до
подписчиков на инстансе B. Простой брокер Spring рассылает только своим локальным сессиям —
без общей шины чат распадается на два независимых чата.

## Решение

Простой брокер плюс мост через Redis pub/sub. `MessageService` кладёт сообщение в PostgreSQL
и публикует его в канал `livedesk:messages`; `RedisMessageRelay` на каждом инстансе подписан
на канал и делает `convertAndSend` своим локальным подписчикам. Инстанс слышит и то, что
опубликовал сам, поэтому рассылка живёт ровно в одном месте.

События очереди ходят тем же способом через канал `livedesk:queue`.

## Последствия

Redis pub/sub доставляет at-most-once: подписчик, лежавший в момент публикации, сообщение
из канала не получит. Компенсация встроена в протокол — сообщение уже лежит в PostgreSQL, и
клиент после переподключения дочитывает пропущенное keyset-запросом истории. Сбой шины не
роняет отправку: `RedisMessageRelay` пишет WARN, сообщение остаётся в базе.

Инфраструктура не растёт: Redis в проекте всё равно нужен под presence.

## Альтернативы

**Внешний STOMP-брокер (RabbitMQ) через broker relay.** Работает и снимает задачу целиком,
но прячет ровно ту механику, которую проект должен показывать, и добавляет в стенд ещё один
сервер с очередями и обменниками.

**Kafka.** Здесь она избыточна: история хранится в PostgreSQL, а не в топике; consumer groups
не нужны — нужен fan-out всем инстансам сразу; строгий порядок с оффсетами чат не требует.
За это платится весом брокера, ZooKeeper-подобной обвязкой и лагом.
